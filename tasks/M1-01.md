## Outcome and boundaries

Deliver a trace-driven map of what the ROM actually executes in two scenarios, with processor-mode context and entry points, and the tool that produces it reproducibly. Unexecuted bytes stay unclassified; nothing is inferred from static analysis alone.

**Part A — coverage capture and the map of the validated scenario.**

1. A whole-run instruction-coverage capture. Decision (coordinator, 11 September 2026): the pinned core and its tracked patch stay unchanged, because every replay manifest and `tools/locks/emulators.json` pin the patch digest `a719f5ffe222…`, so a patch change would be a baseline change for every recorded digest. Instead the existing ring (`trace_entries`, up to 1,000,000 entries of 20 bytes; the hook already records pc, p and e per executed instruction) is **drained once per frame** from Python: after each `retro_run`, read `trace_total`, take the newest `delta` entries of the window and accumulate them. About 14,000 instructions execute per frame in this ROM (8,514,634 over 600 frames, R-0002 finding 7), so a ring of 100,000 or more cannot overflow within a frame; the capture must still check `delta <= capacity` every frame and fail the run (exit 1, reason recorded) if it ever does not hold. Enabling the ring does not alter emulation by construction (the hook only copies registers), and the acceptance table verifies it anyway: the sample digest of `boot-start-600` must be unchanged under capture. Only if this approach proves unusable (measured, for example more than about ten minutes for 600 frames after obvious optimisation such as `struct.iter_unpack` over the raw buffer) may the worker fall back to a core patch extension, and then the lock and every manifest's `patch_sha256` change in one explained commit with every recorded digest re-run and shown unchanged, and the reviewer confirms that re-run.
2. Per executed 24-bit address: execution count, the set of processor modes observed (E, M, X flags from `p` and `e`), the first frame at which it executed, and the ROM file offset it maps to under the LoROM rule (a cartridge address reached through more than one bank is recorded with each bank and one offset). Code executing from work RAM or anywhere outside the ROM is listed separately, not dropped.
3. Opcode lengths under the observed M/X flags classify the operand bytes of executed instructions, so the map distinguishes executed opcode bytes, their operand bytes, and everything else (**unclassified**). Absolute and long operands of executed instructions give a list of *statically referenced* addresses (candidate data, tables or jump targets); indexed and indirect targets are not resolved in this task. Reads and writes are not tracked (the trace does not carry them); a data-access map is a later task if M1-02 or M1-03 needs one.
4. Entry points: the six native-mode and six emulation-mode vectors from the ROM header with their targets and whether each target executed; every executed instruction whose predecessor in the trace is not its sequential successor (subroutine and jump targets, interrupt handlers, returns) with the edge's kind (JSR, JSL, JMP, JML, RTS, RTL, RTI, BRK/COP, interrupt entry, branch), its mode and count. The interrupt entry is not an executed instruction (R-0002 finding 7), so NMI/IRQ handlers are recognised by the target being a vector target.
5. The map for `boot-start-600` (the only validated scenario at dispatch), as a tracked derived file under `docs/map/` plus a short Markdown summary (per-bank executed byte counts, mode mix, entry-point count, how many bytes of the 2 MiB are executed, and the coverage limits), and the evidence record R-0006.

**Part B — a gameplay-reaching scenario.** The boot scenario cannot show where rider state or track data live, and M1-02 and M1-03 depend on this task. Decision (coordinator): the selected gameplay scenario is a cold start driven from the title screen into the **first race of the single-player mode** with a short segment of riding (a few seconds of accelerate/lean input), bounded to at most 3,000 PAL frames (60 s). The worker discovers the menu path by experiment: add a frame-image dump option to the worker (write the XRGB8888 frame at chosen frame numbers as PNG through `zlib`; no new dependency) and look at the images, then encode the discovered presses as a reference script and a replay manifest with the same fields as `boot-start-600`. The scenario is validated the M0-04 way: two fresh runs identical on every declared field (`replay compare` exit 0, expected digests recorded in the manifest), and one perturbation of a riding-phase input (for example removing the accelerate press) produces a first divergence during the riding phase, which shows the inputs reach gameplay code. Then capture coverage for it and produce its map; the summary must list what the race scenario executes that the boot scenario does not (new ranges, new entry points), which is the hand-over to M1-02 and M1-03. Menu choices that the worker makes (mode, track, player) are recorded in the manifest description with their rationale; a wrong but recorded choice is acceptable.

Not in scope: assigning any meaning to a work RAM address (M1-02), decoding any asset or track (M1-03), a data-access (read/write) map, a native simulation, a disassembly listing in tracked files, changes to the pinned core (except the recorded fallback), a Linux run of the core, a scheduler.

Tracked-content rule: tracked map files carry addresses, ranges, offsets, counts, modes, frame numbers, edge kinds and the twelve vector values; they must not carry ROM bytes, opcode bytes or a disassembly (those stay in ignored `artifacts/`). Keep each tracked map file under about 1 MiB by using ranges; per-address detail stays in ignored artifacts and is regenerated by the recorded command.
