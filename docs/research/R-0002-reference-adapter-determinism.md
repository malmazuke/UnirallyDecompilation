# R-0002 — Reference adapter: headless determinism, input delivery and save/restore on the PAL ROM

Task: [M0-03](../../tasks/M0-03.md). Decision: [D-0001](../decisions/D-0001-reference-emulator.md). Recorded 10 September 2026; findings 1, 4–5, 7 and 10–11 revised 11 September 2026 after the first four independent reviews.

## Domain

Verified observations about the laboratory's reference execution, not about the game. Everything below was measured on macOS 15.7.2 arm64 (Apple clang 17.0.0) with:

- ROM: PAL Unirally, SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e` (R-0001), no copier header.
- Core: bsnes commit `7d5aa1e656b9` + `tools/unirally_lab/reference/patches/bsnes-lab-exports.patch` (SHA-256 `a719f5ffe222…`), libretro target, options in `tools/unirally_lab/reference/bsnes.py::DEFAULT_OPTIONS` (`bsnes_entropy=None`, fast PPU/DSP, no run-ahead, no overclock), save-state synchronization method `Strict` unless stated (`--serialization-method`).
- Scripts: `tests/manifests/reference/boot-300.json` (300 frames, no input), `boot-start-600.json` (Start held on controller 1 for frames 300–305), `unreachable.json` (10^9 frames).
- Sampling: after every frame, SHA-256 of the 131072-byte work RAM, the 26-byte CPU register block (PC, A, X, Y, S, D, DB, P, E, MDR, V/H counter, field, WAI, STP), SHA-256 of the XRGB8888 frame buffer and of the 48 kHz stereo audio batch. The run's "sample digest" is a SHA-256 over the initial WRAM/cartridge-RAM digests and every frame's WRAM digest and register block.

## Findings

1. **Cold start is repeatable across processes.** Three fresh `worker.py` processes running `boot-300` produced sample digest `f210eecacf63cbeb…`, video/audio digest `edfa4f8e92b24dc0…` and final serialized-state SHA-256 `df4fb430e731dfe1…` (290457 bytes; the digest was `8e0af6be66113714…`, 290423 bytes, with the first patch and `Fast` synchronization, see finding 5). A clean clone of the repository that cloned the pinned bsnes commit itself, applied the patch and rebuilt the core reproduced the same three digests. Report: `artifacts/m0-03/verify.json` (local) and the clean-clone report listed in the task record.
2. **Power-on state.** With entropy `None`, WRAM is all zeros at power-on (WRAM digest at frame 0 recorded in the samples); cartridge RAM (8192 bytes present for this ROM) starts from the core's allocation fill when no save file exists (`initial.cartridge_ram_sha256` = `7d2c7ac4888bfd75…`). The core writes `<ROM base name>.srm` to its save directory at unload and reads it back at the next load; with a shared directory, run 2 diverged from run 1 at frame 228. Every run therefore gets a private, empty save directory, and the initial cartridge-RAM digest is part of the sample digest.
3. **Serialized state.** Before the patch, two states from identical runs differed in exactly 8 bytes at offsets 542–549, inside bsnes' `Random` state, because the generator is seeded from `clock()` even when entropy is `None` (the generator's output is then unused). The adapter reseeds with `(0, 0)` after load; states from identical runs are now byte-identical.
4. **Serializing runs the cores to a synchronization point.** `retro_serialize` calls bsnes' `runToSave()` before copying the state, so the state corresponds to a sample taken *after* serializing (the CPU has moved past the frame boundary: for example `hcounter` 106 and a different PC), not to the frame-end sample. The worker records that post-serialize WRAM/register sample in the state's sidecar and the restore check compares against it. (The first version of the check compared against the frame-end sample and passed at frame 149 only by coincidence; review finding.)
5. **Restore fidelity.** `restore-check` was run at every save point of both tracked scripts (`boot-300`: 0–298, 299 points; `boot-start-600`: 0–598, 599 points; reports under `artifacts/m0-03/sweep-dense/`), sampling every frame from the save point on in all three runs:
   - `Strict` (adapter default): at all 898 points the restored process matched the post-serialize sample and continued with identical WRAM and registers on every frame to the end, with the same final state. The act of saving changed the continuing run itself (`save_does_not_perturb` failed) at 59 points in each script, the same set in both: 29, 33, 38–39, 41–43 and 45–96. At 4 of them (29, 38, 39, 70) the difference is transient and the final state is identical; at 69 the first difference appears two frames after the save, elsewhere one frame after. No point from 97 on perturbs, including saves taken while Start is held (300–305 in `boot-start-600`). A state taken at a perturbing point is a faithful state of a *different* timeline; the tool reports it, and the uninterrupted run remains the reference.
   - `Fast` (bsnes default) at 50, 63 and 290 of `boot-300`: saving also perturbed the run at 63, so the perturbation is a property of synchronizing during that part of the boot sequence, not of one method. Unlike `Strict`, `Fast` restores diverged at 50 (registers frozen from frame 51, WRAM from 58, game-visible) and at 290 (every sampled frame matched but the final serialized state differed in 54 bytes). bsnes' own source notes that `Fast` can deadlock for some games.
   - Before finding 11 below, a `Strict` save taken while Start was held (`boot-start-600`, save after 300 or 302) restored with WRAM `$7E0073` reading `0x00` instead of `0x10` at the first frame: the Start bit. The patch now serializes gamepad state and those points are exact (second review finding).
   - Resolution of the checks: `restore-check` makes all three runs sample every frame from the save point to the end (`--sample-from-frame`), whatever the script's `sample_every`, so the comparisons have the adapter's full per-frame resolution; with only the script's grid, transient perturbations such as 29, 38, 39 and 70 went unnoticed (fourth review finding). The perturbation window itself was earlier described as "45–91" from 42 sampled points; the dense sweep supersedes that.
   - Consequence: states are validated at capture time by running `restore-check` (which needs an uninterrupted run for comparison); a save point whose `save_does_not_perturb` check fails must not be used as a reference origin. The cause of the 29–96 perturbation region (hypothesis: the boot-time APU upload handshake) is not investigated here.
   - The final serialized-state digest depends on the method and on the state format because the final `retro_serialize` synchronizes too: with the current patch and `Strict` it is `df4fb430e731dfe1…` (290457 bytes) for memory/register sample digest `f210eecacf63cbeb…`. Video of the first restored frame and the resampled audio stream differ from the uninterrupted run under both methods: the frame buffer and resampler state are not part of the serialized state, so video/audio must not be compared across a restore.
6. **Input delivery.** Start held for frames 300–305 produced the first WRAM difference against the no-input run at frame 300 itself, and two repetitions were identical. Start held for frames 200–205 produced no WRAM difference within 600 frames (the game does not react at that point of its boot sequence; the reason is not investigated here). `input_polls` equals the frame count: the core polls once per frame.
7. **Trace window.** The samples record 4,368,044 executed CPU instructions for the 300-frame script and 8,514,634 for the 600-frame one; the count is read after the final `retro_serialize`, whose `Strict` synchronization executes a few more instructions than the frames alone (4,368,042 and 8,514,629 with `Fast`). The last 64 pre-instruction register snapshots are recorded in every samples file. The hook fires only on the `instruction()` path of `CPU::main`: WAI/STP idle iterations and interrupt entry are not counted.
8. **Bounded execution.** `unreachable.json` under `--timeout 3` is killed after 3.0 s; the report records the run as `timeout` and the command exits 4. No partial samples file is produced.
9. **Throughput.** 300 frames with full sampling take about 0.7 s of worker time (about 1.7 ms per frame including the 128 KiB hash); 600 frames 1.3 s.
10. **Environment.** The core asks for libretro environment commands 11, 16, 34 and 35 (input descriptors, variables, subsystem and controller info), which the adapter declines; every run records the set so a core update that needs a new command is noticed. The video digest covers the `pitch × height` frame buffer as delivered, including any row padding.
11. **Controller state.** Upstream `ControllerPort::serialize` is empty, so a gamepad's latch flag, shift counter and the twelve buttons captured at the last latch were not part of a state. `Strict` synchronization stops inside the auto-joypad poll window (vcounter 225, hcounter about 240), after the latch, so a restored process shifted zeros into the remaining bits. The patch adds `Gamepad::serialize` (17 bytes per port); the state size grew from 290423 to 290457 bytes.

## Limits

- Measured on one host and one core build. The library bytes differ between builds of the same source (debug information embeds absolute paths), so reproducibility is claimed for behaviour (sample digests), not for the binary. A state file is tied to the exact library digest, ROM, script and method recorded in its sidecar and is refused otherwise.
- No Linux run of the core yet; CI remains ROM-free.
- The fast PPU/DSP profile is the reference; the cycle-accurate profile was not run.
- Frame-granular input only. Nothing here identifies any gameplay field; that is M1.
- State sidecars are consistency-checked (core, ROM, script and method digests, frame range), not tamper-proof: an `after_frame` edited to another value inside the script's range is accepted and only a `restore-check` against the saving run would expose it.
