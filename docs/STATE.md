## Current facts

- Target baseline: **PAL Unirally (European/Australian version)**. Identified in M0-01: headerless 2 MiB LoROM FastROM image, country code 0x02 (Europe), internal checksum verified, SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e`. See [R-0001](research/R-0001-rom-identity.md). PAL timing and mapping under execution remain unverified.
- The ROM stays outside the repository; ignored `local/rom-location.txt` holds its path and `python3 tools/project.py rom inspect --expect tests/manifests/rom/unirally-pal.json` verifies a copy.
- `tools/project.py` implements `rom inspect`, `doctor`, `bootstrap`, `build --preset` and `test --suite synthetic` with JSON reports (schema 1) and exit codes 0/1/2/3/4 for success, failure, missing prerequisite, invalid input and timeout.
- Pinned CMake 3.31.10 and Ninja 1.13.2 are fetched as digest-verified wheel archives into ignored `local/toolchain/`; bootstrap is idempotent. No dependency is installed globally.
- `src/lab/` is a synthetic C++20 determinism probe, not game code. Its 1000-step state hash `0be347c529fadda9` is identical on macOS arm64 (AppleClang, Homebrew clang, with sanitizers) and Linux x86_64 (GCC 13.3, with sanitizers).
- ROM-free CI (`.github/workflows/synthetic.yml`) runs on `ubuntu-24.04` and `macos-15` for pushes to `main` and `task/**`; both are green at the M0-02 candidate. No private-fixture runner exists.
- Reference adapter (M0-03, [D-0001](decisions/D-0001-reference-emulator.md), [R-0002](research/R-0002-reference-adapter-determinism.md)): a pinned **bsnes** libretro core (commit `7d5aa1e656b9`, tracked patch `tools/unirally_lab/reference/patches/`) driven from Python in fresh worker processes; `python3 tools/project.py reference build|run|verify|restore-check`. On this ROM three fresh processes give identical per-frame work RAM, registers, video and audio (memory/register sample digest `f210eecacf63cbeb…` for `tests/manifests/reference/boot-300.json`); the core reports PAL; inputs are delivered per frame; a save/restore in a fresh process continues identically at every save point of both tracked scripts, while saving at boot-sequence points 29–96 (with holes) perturbs the run, which `restore-check` detects. Video/audio are not restorable. Mesen Community Edition is pinned as an investigation tool only.
- Replay manifests and comparator (M0-04, [R-0003](research/R-0003-replay-comparator.md)): `tests/manifests/replay/*.json` (manifest schema 1: scenario, ROM and core identity, cold-start or validated-state origin, both controllers' frame-timed inputs, declared fields, regeneration command, expected digests) drive `python3 tools/project.py replay validate|run|compare`. Every reference execution is a separate worker process (reference samples schema 2 adds declared work RAM ranges, a stop frame, a WRAM dump and process identity; the M0-03 sample digest is unchanged). On this ROM two fresh runs of `boot-start-600` are identical (sample digest `583d1ec544ec61a2…`); removing or moving the Start press at frames 300–305 is reported as a first divergence at frame 300 and localized to one work RAM byte, `$7E0073` (`0x10` held, `0x00` not), with identical final states; absent ROM/state/evidence exit 2, an unreachable manifest exits 4, invalid manifests exit 3. Two independent reviews with their own withheld perturbations agreed with manual frame-by-frame comparisons. A state is a valid origin only with its restore-check report at the same save point.
- The Python test runner now records failing subtests and `test --suite synthetic` fails when the runner does (a defect since M0-02 that let three erroring subtests read as 101/101 was found by the first M0-04 review). The suite has 118 checks, 110 Python tests.

- Observed code map (M1-01, [R-0006](research/R-0006-observed-code-map.md)): whole-run instruction coverage is captured by draining the pinned core's unchanged trace ring once per frame from Python (`python3 tools/project.py coverage capture|map`; the core patch, lock and every existing manifest and digest are unchanged, and the boot scenario's sample digest is identical under capture). A second validated scenario, `race-crawler-dragster-3000` (cold start, Start presses on the default menu entries 1P → MIKE → CRAWLER → DRAGSTER → Race, Right held from frame 1500 as accelerate, Up 2200–2259 as lean; sample digest `72f618f2f7e3416e…`), reaches gameplay: removing the Right press diverges at frame 1500 in one byte, `$7E0313`. In it 34,900 byte addresses (1.66 % of the ROM, all in banks $00 and $80–$83, i.e. the first 128 KiB) execute, 30,252 of them only in the race; NMIs are off for frames 1208–1328 while the race loads; 10 unknown edges all come from a block-move routine in work RAM at `$00:0199`. Independently reproduced by one reviewer from its own clone, including two own perturbations and frame images. Suite 118 → 148 checks. Observed effort: about 30 min of worker session plus one 10.5 min review (the worker's handoff overstated its own duration; the harness measurement is recorded in the task).
- Trace-derived access record and player state (M1-02, [D-0002](decisions/D-0002-data-access-observation.md), [R-0007](research/R-0007-player-state.md), schema [docs/state/player-state.md](state/player-state.md)): reads, writes and stored values are derived from the unchanged trace ring's per-instruction registers plus the ROM bytes (`python3 tools/project.py access capture|query`; the core, patch, locks, existing manifests and digests are unchanged). On the whole race scenario 25.9 M accesses derive in about 90 s with 0.24 % unresolved (pointers advanced by `INC` within the frame; no unresolved store); two fresh captures are byte-identical. Eleven fields of the race are recorded with their writer pcs and validated by nine new input-variant manifests whose predictions were written before each run: `pos_x` `$7E0415` (opponent `$7E0417`) with `pos[f+1] − pos[f]` equal to the displacement `$7E0BBB` stored in frame f+1 in every checked frame, `speed` `$7E04BB` decaying by exactly 1 per frame after a release, `throttle` `$7E0BEB` ±16 per frame, the race timer digits `$7E0E19`–`$7E0E29` at five PAL frames per tenth matching the on-screen tenths (one game update = one PAL frame from frame 1329; the sample at the end of frame N reflects frame N's inputs, in the order joypad → axes → physics → opponent → camera → timer), the joypad images `$7E0311`/`$7E0313` written right after the `$4218`/`$4219` reads. Lean (Up vs Down leaves no persistent work RAM state), the Y button, and the camera lag rule are recorded as unknown or identified only. Independently reproduced by one reviewer from its own clone with a withheld release at frame 2500; 9 of 10 mutations caught. Suite 148 → 173 checks. Observed effort: about 45 min plus 8 min of worker session (one usage-limit interruption with nothing lost), one 15.5 min review.
- Track and asset decode (M1-03, [R-0008](research/R-0008-track-decode.md), content record [docs/content/dragster-segment.md](content/dragster-segment.md), manifest `tests/manifests/content/dragster-segment.json`): with the PPU ports watched, the access record pairs all 39,705 DMA transfers of the race scenario with their destinations and decodes all 2,708 block moves (menus only). The race content is not moved by DMA or block move during the NMI-off load: a CPU port copier writes the font, BG2 tiles, tile map and palette raw from named ROM offsets, and the DRAGSTER track data (ROM file offset `0x0C0000`, 387 bytes) is an RNC ProPack method-1 stream unpacked by `$81:B8E2` into `$7F:0000`. ## Next work

Milestone M1 is accepted (tag `m1`, [R-0009](research/R-0009-m1-acceptance.md)). The next work is **M2-01, the native movement experiment**, whose record [tasks/M2-01.md](../tasks/M2-01.md) was audited and claimed by the Codex coordinator on 12 September 2026, from `main` after the `m1` tag. The audit fixes the required movement projection before implementation, the initial sample boundary, the speed writer beyond the suggested routine range, and the content prerequisite for native replay. It is the first task that writes game code (`src/core/`) and reads arithmetic from the ROM rather than observing the core: the physics routine `$82:8AB1`–`$82:8DF8` and its reads of the decoded per-tile table and the undecoded ROM tables in banks $20/$21, reproduced per PAL frame against the explicit movement projection of `tests/manifests/fields/player-state-v1.json` specified in the task; all eleven reference ranges remain evidence, with out-of-scope fields reported separately. Two rules the record makes binding, from the work order: the primary and withheld reference cases are frozen with reference-derived expected values **before** any native code computes a field, and an unexplained step is recorded as unexplained rather than approximated with a constant that happens to match. M2-02 (state restore and portability, including the first Linux build of the pinned core) follows it; the M1 unknowns listed in R-0009 are M2-01's inputs, not blockers, except that the bank $20/$21 tables may have to be decoded before the displacement arithmetic can be reconstructed, which the plan's estimate carries as its spread. Known limits carried forward: reference execution on one macOS host, ROM-free CI, no lease store for a shared queue, orphaned workers on parent kill (R-0004 G2), the D-0002 residual, and the open notes above.

Implementation choices should be made through bounded experiments. Remote hosting beyond the private repository, release license/distribution arrangements, online service topology, public accounts/ranking and paid execution budgets remain undecided and do not block M1. A Linux build of the pinned core (ROM-free) is a natural CI addition when convenient.
