## Outcome and boundaries

Deliver a native C++20 implementation of the riding update of the validated race scenario that reproduces the declared player-state fields exactly, per PAL frame, against the frozen reference, with the arithmetic read from the ROM rather than fitted to the observations.

**Freeze first (before any tuning).** Write the primary case and at least two withheld input variations into `tests/manifests/native/` and record their expected per-frame field values from the *reference* (not from the native candidate) in the first commit of the task, before the native routine computes anything. The primary case is the riding phase of `race-crawler-dragster-3000` from frame 1534. The withheld variations must be chosen after looking at the game's behaviour and must not be used while developing the routine: at least one different release frame (M1-02's reviewer used 2500, M1-02's worker 2000, so pick another) and at least one input pattern not yet recorded anywhere in the repository (for example an alternating Right/no-Right cadence, or Left applied while moving). The reviewer owns at least one further withheld case. A case whose expected values come from the candidate rather than the reference is a defect, not evidence.

**Read the arithmetic, do not fit it.** The physics routine is `$82:8AB1`–`$82:8DF8` (R-0007 finding 10 gives its reads and writes; R-0006's map gives its ranges and entry points; `coverage map --detail` regenerates a per-address listing under ignored `artifacts/`). Disassemble it locally (the listing stays untracked, per the M1 tracked-content rule), and implement each step with the operand widths, signedness, wrapping and ordering the instructions show. Record in R-0010, per field, the instruction sequence that produces it and the exact integer expression implemented, so a reader can check the code against the ROM without re-deriving it. Where the routine reads a table (the decoded per-tile table of R-0008, or the undecoded ROM tables in banks $20/$21), read the table through the content tooling or record the read values from the access record and state which of the two the native code uses. **Do not invent a mechanism for anything the trace does not show**: an unexplained step is recorded as unexplained and its field is reported as not reproduced, not approximated with a constant that happens to match.

**Compare per frame.** `python3 tools/project.py native compare --manifest <native case> [--from-frame N] [--to-frame N] --report <json>` runs the native simulation over the case's frames and compares every declared field against the reference values, emitting a first-divergence report in the shape `replay compare` uses (frame, field, native value, reference value, the prior frame's values and the inputs of both frames). Exit codes follow the repository convention. The native side must be driven by the same input series the replay manifest declares, and its state must be serializable so that M2-02 can restore and continue it.

Deliverables: `src/core/` with the update and its state type (explicit widths, no undefined overflow, no host byte-order or padding assumptions in the serialization); `tools/unirally_lab/native/` and the `native` command group; the frozen cases under `tests/manifests/native/`; C++ and Python tests, including a case that exercises the first-divergence report on a deliberately wrong native value; R-0010 with the per-field arithmetic and the results; the command-table rows; this record's handoff.

Not in scope: rendering, audio, the menu path, the opponent's AI (its position field is reproduced only if the same routine writes it), tricks and jumps (unvalidated in M1), other tracks or riders, save/restore continuation (M2-02), a playable build (M3), any change to the reference side or to the field schema.

Tracked-content rule: no ROM bytes and no disassembly listing in tracked files. Constants the native code needs are written into the source as named values with the ROM file offset they came from in a comment, and R-0010 records the offsets; a table of more than a few entries is loaded through the content tooling from the ROM at runtime, never pasted into the repository.
