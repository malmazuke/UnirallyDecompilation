# R-0008 — Provenance and decode of the DRAGSTER race content

- Task: [M1-03](../../tasks/M1-03.md); content record [docs/content/dragster-segment.md](../content/dragster-segment.md); manifest `tests/manifests/content/dragster-segment.json`
- ROM: PAL Unirally, SHA-256 `a1105819d48c04d6…` (R-0001); core: pinned bsnes `7d5aa1e656b9` with the tracked patch (D-0001), unchanged; scenario `race-crawler-dragster-3000` (sample digest `72f618f2f7e3416e…`, unchanged under every capture below)
- Method: M1-02's trace-derived access record (D-0002) with the PPU address and data ports watched, the block-move pc watched and a per-frame work RAM series of the tile-map staging buffers; whole-WRAM dumps from the worker's `--stop-after-frame`/`--wram-dump-out`; the ROM's routines disassembled locally (not tracked) to name entry points and to port the decompressor; ROM-free tests on synthetic data (`tests/tooling/test_content.py`, 18 tests; suite 173 → 191 checks)
- Status: candidate for review. Everything below is observed on this ROM and this scenario unless marked as a limit.

## Findings

1. **Inventory (part A).** The whole-run access record with the ports watched (`access.json` SHA-256 `11bb8622e7db6637…`, 85 s) holds 39,705 MDMAEN stores, equal to the record's `residual.dma_triggers` (M1-02: 39,705) and 1,754 HDMAEN stores; every store enables exactly one channel, so `content provenance` lists 39,705 channel transfers: 36,791 ROM→VRAM (1,193,376 bytes), 1,886 work RAM→VRAM (318,940 bytes), 936 work RAM→OAM (509,184 bytes; the 544-byte OAM image), 92 ROM→CGRAM (23,304 bytes). 39,558 transfers have a paired destination; the 147 without are OAM uploads of frames 99–403 whose OAMADD write went through the `$80:2102` mirror, which the capture did not watch (`$00:2102` was). Frames 1200–1400 contain 1,892 transfers: 1,827 sprite tiles of 32 bytes from ROM, 40 BG1 tile halves of 64 bytes from ROM (frame 1242), 10 OAM images (frames 1200–1207 by `$80:9338`, 1332–1333 by `$82:D37A`), 9 rows of 34 bytes from `$00:0437` and 6 columns of 32 bytes from `$00:0459`. The block-move routine at `$00:0199` executed 88,769 times in 2,708 transfers, all in frames 404–1054 (menus): 2,677 read ROM (the record's block-read range for the pc is `$27:8000`–`$83:A1DA`), 23 read `$77:000C`–`$77:037F` (the LoROM cartridge-RAM region) and 8 read `$80:0010` (a work RAM mirror); every transfer's length equals its count register plus one. **No block move and no DMA moves the race content during the load phase (frames 1208–1328, NMIs off).**

2. **Load phase.** The race content reaches the PPU by CPU port writes, not DMA: `$82:D4B8` clears VRAM (32,768 word stores, frames 1208–1214) and `$82:D4C7`/`$82:D4D0` CGRAM; the copier entered at `$82:B1DB` (VRAM) and `$82:B183` (CGRAM) resolves a directory entry (5 bytes at `[$4F]`, default `$82:B332`: bank|flag, address, length) and copies bytes one at a time through `$82:B296` (`LDA $0000,Y`, bank wrap at `$8000`) to `$2118`/`$2119` or `$2122`. Reconstructing the watched port writes of frames 1208–1242 gives VRAM bytes `0x0000`+2048, `0x0801`+3, `0x2000`+992, `0xE000`+8192 and CGRAM 256+96 bytes, and the copier's recorded ROM reads in that window are exactly the source ranges `0x05BCC0`+10240 (font then tile map), `0x058000`+992, `0x07B540`+32, `0x07B760`+192, `0x07B9A0`+32, `0x020180`+32, `0x020380`+64 — byte for byte equal to the reconstructed VRAM/CGRAM bytes (raw copies). The CGADD sequence of frames 1219–1220 is `$70, $00, $10, $20, $30, $40, $50, $B0, $F0, $C0, $80`, 16 colours each.

3. **Track data.** `$82:E12B` (entered at frame 1220) clears `$7E:20A8`–`$7E:FFFE`, then loads asset `$77:074A + $C2` through `$82:B2DD`: entry `0xC2` = bank `$18` with the compressed flag, `$8000`, length 387 → `$82:B323` → `JSL $81:B8E2` with the destination `$7F:0000`. The block starts with an `RNC\x01` header (Rob Northen ProPack method 1: unpacked 0x8417, packed 0x171, 4 chunks). The register-level port of `$81:B8E2` (`tools/unirally_lab/content/rnc.py`) consumes `$18:8011`–`$18:8183` and produces 33,815 bytes (SHA-256 `8f5cef67dc57977a…`) equal to `$7F:0000`–`$7F:8416` of the whole-WRAM dump after frame 1243 except `$7F:000B`, which the loader increments as it walks the tile-set list (`$82:E1A7`, 0x0F → 0x16). A first port with a mis-read base table (the entries above 128 at `$81:BA4B` are 1 << k, not a repeat) stopped at 13,085 bytes with the correct prefix, which is how the error was found. The recorded resolved reads of the routine end at `$18:8183` as the port does.

4. **BG1 tiles and per-tile tables.** The decoded block ends with the tile-set list `01 02 14 24 16 18 FF` at offset `0x840F`. For each id the loader resolves the tile directory at `$82:B7DD` (`$16:8080` 1 tile, `$16:8100` 1, `$16:D900` 4, `$16:FF80` 9, `$16:DD00` 4, `$16:E100` 1; 128 bytes per 16×16 tile in groups of eight top rows then eight bottom rows) and DMAs 64-byte halves to VRAM words `$2000 + n·$20` and `+$100` — the 40 transfers of frame 1242 listed in the inventory match the directory exactly (20 tiles, 2,560 bytes, SHA-256 `5a45c158da5565b8…`). It also copies, per id, `length/4` bytes from the pointer at `$17:A000 + 4·id` to `$7E:A000` and `length/128` bytes from `$17:C4E4 + (pointer − $A0A4)/32` to `$7E:C000`; the six ROM pieces (640 and 20 bytes) equal the dump's `$7E:A000`–`$7E:A27F` and `$7E:C000`–`$7E:C013` byte for byte.

5. **Riding.** From frame 1334 every frame starts 26–28 channel-0 DMAs: one 32-byte tile per rider frame tile from ROM banks `$27`–`$39` to the OBJ name area (the unrolled sequence `$82:B907`–`$82:BDC0`; 27 tiles at frame 1600, 21 at 2400), and one 32-byte tile-map column from `$00:0437` with VMAIN `$81` to consecutive columns of the BG1 map at word `$0C00` (`$0D8E`…`$0D96` in frames 1590–1600; the first riding frames also send 34-byte rows from `$00:0459`). The staging buffers are filled by `$81:B3D3` (`STA $0000,Y`) from `$7F:000F,X` (the column builder `$81:B31C`: X = column·32 + `$0234` + `$0559`, stepping by `$0236`). OAM is uploaded once (frames 1332–1333, `$00:138B`); afterwards only sprites 96–99 and one high-table byte are rewritten per frame through `$2104`. Scroll comes from HDMA tables in work RAM (BG1 `$7E:2046`, BG2 `$7E:2058`, one entry of 112 lines, so constant within a frame); BG1SC from `$7E:207F`; colour math and the GO-letter window from channels 5 and 6.

6. **Decode is exact (part B).** `content decode` reproduces every manifest item's digest from the ROM (report `fbcd1ecd236c4ee1…`); with the dump after frame 1243 it shows `track-data` 33,814/33,815 bytes equal (the cursor byte listed as a known runtime write), `tile-tables` 640/640 and `tile-flags` 20/20.

7. **Runtime rendering comparison.** `content compare` rebuilds VRAM/CGRAM/OAM at the frame from the decoded items and the record (ROM→VRAM DMAs and the column DMAs replayed — the column DMA of frame N copies the staging buffer of the series entry N − 1, since the DMA runs in the vblank that starts the frame and the game loop of frame N rebuilds the buffer afterwards; CGRAM and OAM port writes from the windowed records with `$2121`/`$2122`/`$2102`/`$2104` watched; scroll from the dump after the frame), renders BG2, BG1 and sprites with the core's colour conversion (5-bit channel replicated, then gamma 1.5 on the lower half as `target-libretro/program.cpp` does; the channel order calibrated as SNES `0BBBBBGGGGGRRRRR`) and a background row of `VOFS + y + 1`, and compares with the frame image: frame 1600, rectangle (120, 28, 136, 196): 490 of 26,656 pixels differ (1.84 %; report `7cc7468d929340be…`); frame 2400, rectangle (0, 28, 256, 196): 791 of 50,176 (1.58 %; `861498a14530b35c…`). The differing pixels are, first, a full-width band of four lines just below the ribbon at every compared frame (rows 154–157 at 1600, 149–152 at 2400, fixed relative to BG1 VOFS; 512 of the 791 mismatches at 2400): the renderer draws BG1 palette-0 entries 1 and 3 there while the original shows colours that occur nowhere in the reconstructed CGRAM, because HDMA channel 5 writes `$2131`/`$2132` (colour math and fixed colour) from the table at `$7E:2084` on those lines — a declared omission, located by review 1 (the submitted text attributed all mismatches to the HUD text); second, the HUD text (BG3, not rendered); and, at 1600, the edge of the window-drawn G; the wall pattern, the track ribbon's green/blue columns and both riders coincide pixel for pixel. Before the two calibrations the counts were 7,689 (BG2 one line off) and 2,167 (columns one frame off); the scan over ±3 pixels of BG1/BG2 scroll confirmed the HDMA table values with the +1 line rule. The 54 distinct colours of the frame are all produced by the converted CGRAM.

8. **Collision/geometry table.** The riding physics reads the per-tile column table through `$81:8CBB` (`LDA $7EA000,X`) and `$81:8CDD` (`LDA $7EA001,X`), 20 executions per frame, and the flags through `$81:8C0C`/`$81:82D9` (`$7E:C001`). Load values from watched captures: at frame 1574 `$81:8CBB` reads `$7E:A116` = 160 (0xA0) twice — the decoded `tile-tables` byte at offset `0x116`, which is ROM file offset `0x0BC3DA` in tile set 36's table (`tile-tables` piece 4, offset 0x56); at frame 1600 `$81:8CBB`/`$81:8CDD` read `$7E:A024`/`$7E:A025` = 0 (tile set 2, ROM `0x0BA0C8`/`0x0BA0C9`). In this scenario every table byte the physics reads is 0 or 0xA0 (flat ribbon or no surface); the table's meaning (a height per 16-pixel column, 0xA0 as "no surface", with a second byte compared at `$81:8CBF`) is a hypothesis, not established. ROM reads during riding by code in banks `$81`/`$83` from ROM banks `$20`/`$21` (`$83:F2F1`/`$83:F2FB` `$20:8000`–`$20:A840`, `$81:9E42`–`$81:9E54` `$21:8000`–`$21:AE06`, `$81:9E7B`–`$81:9EEA` `$20:BC9F`–`$20:BCAD`, 184–368 reads in frames 1329–1420) are the remaining candidate tables, named and left undecoded.

## Limits

- The tile map region is not decoded from the `$7F` block into map coordinates: the column builder's gather (`$7F:000F,X` with the `$0234`/`$0236`/`$0559` variables) was read but not reproduced, and a stride search over the decoded block did not find the staged columns verbatim. The rendered BG1 map is the original's own upload sequence (staging buffers from the series), so the comparison shows the decoded block is what the original used through `$81:B3D3` only indirectly; reproducing the gather is the next experiment.
- The tile-set list, the header words and the geometry regions of the decoded block are located, not interpreted.
- The palette's per-frame rewrites (colour 0, colours 96–111) come from the record, not from a decoded table.
- The renderer omits windows, colour math, BG3, per-scanline register changes, mosaic, offset-per-tile, sprite-per-line limits and fine priority; the mismatch counts include those.
- The block-move inventory's source banks for ROM transfers are given as the pc's block-read range (the record aggregates ROM reads per pc), not per transfer.
- Reference execution on one macOS host; CI is ROM-free (the new tests use a hand-built RNC stream and synthetic tiles/records).
