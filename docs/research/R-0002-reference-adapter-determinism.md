# R-0002 — Reference adapter: headless determinism, input delivery and save/restore on the PAL ROM

Task: [M0-03](../../tasks/M0-03.md). Decision: [D-0001](../decisions/D-0001-reference-emulator.md). Recorded 10 September 2026; findings 4–5 and 10 revised 11 September 2026 after the first independent review.

## Domain

Verified observations about the laboratory's reference execution, not about the game. Everything below was measured on macOS 15.7.2 arm64 (Apple clang 17.0.0) with:

- ROM: PAL Unirally, SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e` (R-0001), no copier header.
- Core: bsnes commit `7d5aa1e656b9` + `tools/unirally_lab/reference/patches/bsnes-lab-exports.patch` (SHA-256 `04267fc82746…`), libretro target, options in `tools/unirally_lab/reference/bsnes.py::DEFAULT_OPTIONS` (`bsnes_entropy=None`, fast PPU/DSP, no run-ahead, no overclock), save-state synchronization method `Strict` unless stated (`--serialization-method`).
- Scripts: `tests/manifests/reference/boot-300.json` (300 frames, no input), `boot-start-600.json` (Start held on controller 1 for frames 300–305), `unreachable.json` (10^9 frames).
- Sampling: after every frame, SHA-256 of the 131072-byte work RAM, the 26-byte CPU register block (PC, A, X, Y, S, D, DB, P, E, MDR, V/H counter, field, WAI, STP), SHA-256 of the XRGB8888 frame buffer and of the 48 kHz stereo audio batch. The run's "sample digest" is a SHA-256 over the initial WRAM/cartridge-RAM digests and every frame's WRAM digest and register block.

## Findings

1. **Cold start is repeatable across processes.** Three fresh `worker.py` processes running `boot-300` produced sample digest `f210eecacf63cbeb…`, video/audio digest `edfa4f8e92b24dc0…` and final serialized-state SHA-256 `8e0af6be66113714…` (290423 bytes). A clean clone of the repository that cloned the pinned bsnes commit itself, applied the patch and rebuilt the core reproduced the same three digests. Report: `artifacts/m0-03/verify.json` (local) and the clean-clone report listed in the task record.
2. **Power-on state.** With entropy `None`, WRAM is all zeros at power-on (WRAM digest at frame 0 recorded in the samples); cartridge RAM (8192 bytes present for this ROM) starts from the core's allocation fill when no save file exists (`initial.cartridge_ram_sha256` = `7d2c7ac4888bfd75…`). The core writes `<ROM base name>.srm` to its save directory at unload and reads it back at the next load; with a shared directory, run 2 diverged from run 1 at frame 228. Every run therefore gets a private, empty save directory, and the initial cartridge-RAM digest is part of the sample digest.
3. **Serialized state.** Before the patch, two states from identical runs differed in exactly 8 bytes at offsets 542–549, inside bsnes' `Random` state, because the generator is seeded from `clock()` even when entropy is `None` (the generator's output is then unused). The adapter reseeds with `(0, 0)` after load; states from identical runs are now byte-identical.
4. **Serializing runs the cores to a synchronization point.** `retro_serialize` calls bsnes' `runToSave()` before copying the state, so the state corresponds to a sample taken *after* serializing (the CPU has moved past the frame boundary: for example `hcounter` 106 and a different PC), not to the frame-end sample. The worker records that post-serialize WRAM/register sample in the state's sidecar and the restore check compares against it. (The first version of the check compared against the frame-end sample and passed at frame 149 only by coincidence; review finding.)
5. **Restore fidelity depends on the synchronization method.** Sweep of `restore-check` over save points with `boot-300` (0, 10, 20, …, 290, 295, 298 plus 45, 55, 275, 285: 36 points) and `boot-start-600` (100, 299, 310, 400, 500, 598):
   - `Strict` (adapter default): the restored process matched the post-serialize sample and continued with identical WRAM and registers on every sampled frame, ending in the same final state, at all 42 save points. The act of saving, however, changed the continuing run itself (`save_does_not_perturb` failed, first difference at the next frame) at 7 of 36 `boot-300` points, all inside frames 45–90, and at none of the `boot-start-600` points. So a state taken there is a faithful state of a *different* timeline; the tool reports this, and the uninterrupted run remains the reference.
   - `Fast` (bsnes default): saving never changed the continuing run (9 of 9 points), but the restored process diverged at 2 of 9 points: after frame 50 the registers stayed frozen from frame 51 and WRAM diverged from frame 58 (game-visible; the saving run's X/Y advance by ±787/788 per frame in a transfer loop while the restored run's do not); after frame 290 every sampled frame matched but the final serialized state differed in 54 bytes (CPU status/DMA region and PPU/DSP tail). bsnes' own source notes that `Fast` can deadlock for some games.
   - Consequence: states are validated at capture time by running `restore-check` (which needs an uninterrupted run for comparison); a save point whose `save_does_not_perturb` check fails must not be used as a reference origin. Frames 45–90 of the boot sequence are such points for this ROM; the cause (hypothesis: the boot-time APU upload handshake) is not investigated here.
   - The final serialized-state digest depends on the method because the final `retro_serialize` synchronizes too: `8e0af6be66113714…` with `Fast`, `8b0a653c8b93c0fb…` with `Strict`, for the same memory/register sample digest `f210eecacf63cbeb…`. Video of the first restored frame and the resampled audio stream differ from the uninterrupted run under both methods: the frame buffer and resampler state are not part of the serialized state, so video/audio must not be compared across a restore.
6. **Input delivery.** Start held for frames 300–305 produced the first WRAM difference against the no-input run at frame 300 itself, and two repetitions were identical. Start held for frames 200–205 produced no WRAM difference within 600 frames (the game does not react at that point of its boot sequence; the reason is not investigated here). `input_polls` equals the frame count: the core polls once per frame.
7. **Trace window.** The instruction hook counted 4,368,042 executed CPU instructions in 300 frames and 8,514,629 in 600; the last 64 pre-instruction register snapshots are recorded in every samples file. The hook fires only on the `instruction()` path of `CPU::main`: WAI/STP idle iterations and interrupt entry are not counted.
8. **Bounded execution.** `unreachable.json` under `--timeout 3` is killed after 3.0 s; the report records the run as `timeout` and the command exits 4. No partial samples file is produced.
9. **Throughput.** 300 frames with full sampling take about 0.7 s of worker time (about 1.7 ms per frame including the 128 KiB hash); 600 frames 1.3 s.
10. **Environment.** The core asks for libretro environment commands 11, 16, 34 and 35 (input descriptors, variables, subsystem and controller info), which the adapter declines; every run records the set so a core update that needs a new command is noticed. The video digest covers the `pitch × height` frame buffer as delivered, including any row padding.

## Limits

- Measured on one host and one core build. The library bytes differ between builds of the same source (debug information embeds absolute paths), so reproducibility is claimed for behaviour (sample digests), not for the binary. A state file is tied to the exact library digest, ROM, script and method recorded in its sidecar and is refused otherwise.
- No Linux run of the core yet; CI remains ROM-free.
- The fast PPU/DSP profile is the reference; the cycle-accurate profile was not run.
- Frame-granular input only. Nothing here identifies any gameplay field; that is M1.
