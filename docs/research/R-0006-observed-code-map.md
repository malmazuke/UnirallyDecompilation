# R-0006 — Observed code map: whole-run instruction coverage of the boot and first-race scenarios

- Status: observed (single host; independent review pending)
- Related task/decision: [M1-01](../../tasks/M1-01.md); builds on [R-0002](R-0002-reference-adapter-determinism.md) finding 7 (trace ring) and [R-0003](R-0003-replay-comparator.md) (manifests and comparator). Coordinator decision recorded in M1-01: the pinned core and its patch stay unchanged; the existing ring is drained from Python once per frame.
- Tested domain and excluded cases: which ROM bytes the CPU executes, under which processor modes and through which control-flow edges, in two cold-start scenarios of the PAL ROM on the pinned core: `boot-start-600` (600 frames, title screen to main menu) and `race-crawler-dragster-3000` (3000 frames, main menu to the first race of the single-player mode with 30 s of riding). Excluded: any meaning of a work RAM address (M1-02), any asset or track decode (M1-03), reads and writes (no data-access map), indexed and indirect operand targets, code executing from work RAM (listed, not decoded), Linux, the cycle-accurate PPU profile, any other menu path, track, tour or rider.
- ROM hash, emulator revision/configuration and adapter version: ROM SHA-256 `a1105819d48c04d680c8292bbfa9abbce05224f1bc231afd66af43b7e0a1fd4e` (R-0001), 2,097,152 bytes, no copier header, LoROM header at file offset 0x7FC0; bsnes `7d5aa1e656b9` with patch `a719f5ffe222…` (unchanged), options as `bsnes.DEFAULT_OPTIONS`, `Strict` synchronization; reference samples schema 2; replay manifest schema 1; coverage document schema 1; map schema 1; macOS 15.7.2 arm64, Apple clang 17.0.0, Python 3.14.3.
- Addresses: `$BB:AAAA` is a 24-bit CPU bus address (bank, offset). ROM file offsets follow the LoROM rule of bsnes board `LOROM-RAM#A` for this cartridge (map mode 0x30, cartridge type 2, 8 KiB save RAM, 2 MiB): banks $00–$6F and $80–$EF at offsets $8000–$FFFF, file offset = ((bank & $7F) << 15 | (address & $7FFF)) mod 2 MiB, so every ROM byte is reachable through at least the slow bank ($00–$3F) and the fast mirror ($80–$BF). Processor mode is written `E`/`N` (emulation/native), `m`/`M` (8/16-bit accumulator), `x`/`X` (8/16-bit index), taken from the pre-instruction P and E registers the hook records; in emulation mode M and X read as 1.
- Input/reset/snapshot identity and hashes: cold start in both scenarios; inputs as in the manifests `tests/manifests/replay/boot-start-600.json` (expected sample digest `583d1ec544ec61a2…`, final state `1a6fbf6d24c532ff…`) and `tests/manifests/replay/race-crawler-dragster-3000.json` (expected sample digest `72f618f2f7e3416e…`, final state `0f3cc38bd5d64401…`, recorded from the two identical fresh runs of finding 5).
- Experiment source commit and exact command: the M1-01 task record's handoff names the candidate commit; the commands are the maps' `regeneration_command` values (`coverage capture` then `coverage map`), the manifests' `regeneration_command` values and `replay compare --against` for the perturbation.
- Artifact location, hashes and regeneration procedure: ignored `artifacts/m1-01/` on the worker host (captures `cap1`/`cap2`/`race-cap1`/`race-cap2`, maps `map1`/`map2`/`race-map1`/`race-map2` with per-address detail, exploration runs `explore1`–`explore5-*` with frame images, reports); tracked outputs under `docs/map/`. Coverage file SHA-256: `1e6c02747d7c1003…` (boot) and `a075220e58ecd355…` (race), identical in two fresh processes each. Report digests are listed in the task handoff.

## Observation

### Capture method

1. **Per-frame drain of the unchanged ring.** `worker.py --coverage-out` enables the existing trace ring with 262,144 entries (22 bytes each: pc, A, X, Y, S, D, DBR, P, E, V/H counters) instead of 64, and after every `retro_run` reads `unirally_trace_total`, copies the whole ring (oldest first) and keeps the newest `delta` entries. Per distinct *site* (24-bit pc, 3-bit mode, data bank) it accumulates the execution count and the first frame; per consecutive pair of sites the step count, carried across frame boundaries; per frame the delta; per watched address (the four interrupt vector targets) the executions per frame; and the newest 64 sites. A delta above the capacity raises an error, the coverage file is written with `status: failed` and the worker exits 1. The largest frame delta observed was 18,346 instructions (boot) and 19,410 (race); the smallest 10,289 (frame 0). The ring cannot overflow in one PAL frame: about 425,000 master cycles at no fewer than 6 cycles per instruction bound a frame to roughly 71,000 instructions.
2. **The capture does not perturb the run.** With the drain enabled the sample digest and final state of `boot-start-600` are exactly the manifest's (`583d1ec544ec61a2…`, `1a6fbf6d24c532ff…`), and the race manifest's two fresh runs without coverage (`replay compare`, finding 5) give the digests the coverage captures reproduce (`72f618f2f7e3416e…`, `0f3cc38bd5d64401…`). The instruction total at the end of the last frame equals the sum of the per-frame deltas: 8,514,628 for 600 frames (8,514,634 after the synchronizing final serialize, the six-instruction difference already recorded in R-0003 finding 6) and 49,465,866 for 3000 frames (49,465,872 after the final serialize). The ring total before frame 0 is 0, so nothing executes between `retro_load_game` and the first `retro_run`.
3. **Repeatability and cost.** Two fresh-process captures of each manifest wrote byte-identical coverage files (boot `1e6c02747d7c1003…`, race `a075220e58ecd355…`), and `coverage map` derived byte-identical map files from each pair (boot map `21c0526c5c51ad67…`, race map `e2c9da7c1509e350…`). The worker takes 4.5 s for 600 frames with the drain (1.3 s without) and 25.0 s for 3000 frames; the map derivation under 0.5 s. The fallback to a core patch was not needed.
4. **The samples' trace window is a suffix of the capture.** In both scenarios the 64-entry window the samples file records at the end of the run equals the last 64 sites of the coverage tail (pc, mode and data bank), checked by `trace_window_is_suffix_of_capture`. Spot checks of the boot window against the per-address detail: `$82:8038` PHX (1 byte, mode NMX, p = 0x05) → `$82:8039` PHY (1) → `$82:803A` SEP #imm (2) → `$82:803C` LDA (3 bytes under Nmx) → `$82:803F` CMP long (4) → `$82:8043` BNE (2): the decoded lengths chain through exactly the addresses the window shows, and the last window entry (pc `$82:8038`, mode NMX, DBR 0) corresponds to the site record with 124,406 executions from frame 406 (the address itself executed 289,405 times from frame 97 under other data banks). The race window agrees the same way.

### The boot scenario (`boot-start-600`, [map](../map/boot-start-600.map.json), [summary](../map/boot-start-600.md))

5. **Extent.** 4,648 executed byte addresses (2,085 opcode bytes + 2,563 operand bytes at 24-bit addresses; folded to ROM offsets the same 2,085 + 2,563 = 4,648, i.e. no byte is executed through two banks in this scenario), 0.222 % of the ROM; 2,092,504 bytes unclassified; no byte is both opcode and operand. Executed bytes by bank: $00 34, $80 2,812, $82 633, $83 1,169; 75 maximal ranges. 2,506 sites at 2,085 instruction addresses; 353 entry points.
6. **Vectors and modes.** The emulation reset vector `$00:8858` is the first executed instruction (mode Emx), executed once; the program is in native mode from the fourth instruction on (the three Emx instructions are JMP at `$00:8858`, CLC at `$00:91D1` and XCE at `$00:91D2`). The native NMI vector `$00:8587` executes exactly once per frame from frame 250 to 599 (350 executions; 0 in frames 0–249, never twice) and is the only interrupt target that executes (`interrupt entry` edges: 350, RTI edges: 350). The native IRQ/BRK/COP vectors ($00:8583, $00:857F, $FFFF), the emulation NMI/COP/ABORT ($FFFF) and emulation IRQ/BRK ($00:8583) never execute. Instructions by mode: NmX 4,257,037, Nmx 2,313,127, NMX 1,944,452, NMx 9, Emx 3. Eighteen addresses execute in more than one mode, among them the NMI handler entry `$00:8587`–`$00:8589` (NMX, NmX, Nmx: the handler is entered in whatever mode the main program was in) and `$80:C3C0`, `$80:FBC3`.
7. **Edges.** 1,880,931 non-sequential steps against 6,633,696 sequential ones: branch 1,082,888, JSL 289,446 / RTL 289,443, JSR 108,570 / RTS 108,568, JML 1,051, JMP 13, interrupt entry 350, RTI 350, unknown 252 (5 distinct edges). Every unknown edge starts at a site in work RAM: `$00:0199` (239 executions from frame 404, 227 of them stepping to itself, which is the signature of a block-move instruction re-executing per byte) and `$00:019C` (12 executions, stepping to `$80:AD79` and `$83:96FB`). No edge from a ROM site is unclassified, which is the whole-run check of the length table: a wrong length would surface as unknown edges or as opcode/operand overlap, and neither occurs. 258 statically referenced addresses (absolute operands with the observed data bank, long operands).

### The race scenario (`race-crawler-dragster-3000`, [map](../map/race-crawler-dragster-3000.map.json), [summary](../map/race-crawler-dragster-3000.md))

8. **Menu path discovered by frame images.** With Start held at 300–305 the title screen (frame 299) gives way to the main menu `1P / 2P / VS / LEAGUE / OPTIONS` with the cursor on `1P` (frame 599). Each further Start press, 130–150 frames apart, accepts the default entry of the next screen: `PICK YOUR UNI` (MIKE, cursor at frame 700), `PICK TOUR` (CRAWLER, frame 820), `PICK TRACK` for the Crawler tour (DRAGSTER; also ZOOM ZOO, BOWL, SWITCHER, MONSTER; frame 1000), `NOW PLAYING: MIKE vs BRONSEN, racing on DRAGSTER — Race / Exit` (frame 1250). After Start at 1200–1205 the race is on screen at frame 1400 with the timer at 0:00:0. Holding buttons from frame 1500: **Right** moves the rider along the track (it passes the opponent, `+0:00:1` at frame 2400, and the hint `PULL A STUNT` appears by 2999); B, Y, A, X and Up each change work RAM from frame 1500 but only Right changes the video output while stationary; Up while riding tilts the rider (frame 2230). The scenario therefore holds Right at 1500–2999 and Up at 2200–2259. Every choice is a default so the path needs no cursor movement; the frame numbers leave about 100 frames of slack after each screen change (a wrong but recorded choice would show in the frame images the capture writes with `--frame-image`).
9. **Validated the M0-04 way.** `replay compare --manifest race-crawler-dragster-3000.json`: two fresh worker processes identical on all three declared fields over 3000 frames, identical final states and video/audio digests, exit 0 (15.5 s). Against the tracked perturbation `race-crawler-dragster-3000-right-removed` (the Right press removed, everything else identical): first divergence at frame 1500 in `wram_sha256` only (the declared range `$7E0000`–`$7E01FF` and the registers agree on that frame), final states differ (`0f3cc38bd5d64401…` vs `fc20c533f3310af2…`), exit 1; localization re-runs to the end of frame 1500 find exactly one differing work RAM byte, `$7E0313` (`0x01` with Right held, `0x00` without), no register difference, consistent with the first runs. The riding input reaches the game at the frame it is applied. Whether `$7E0313` is the joypad image or a derived flag is not claimed (M1-02).
10. **Extent.** 34,900 executed byte addresses (14,727 opcode + 20,173 operand), 1.664 % of the ROM, 2,062,252 bytes unclassified, no overlap; by bank $00 34, $80 7,083, $81 10,225, $82 11,689, $83 5,869 (no bank above $83 executes, so at most the first 128 KiB of the ROM holds code in these scenarios; the remaining 1.875 MiB is unclassified, not "data"); 675 ranges; 15,912 sites at 14,727 instruction addresses; 2,162 entry points; 114 addresses in more than one mode; 1,691 statically referenced addresses (968 in work RAM, 395 in ROM, 328 elsewhere, e.g. registers), 387 of them code targets of JSR/JMP/JSL/JML. Instructions by mode: NmX 25,090,472, NMX 13,114,254, Nmx 6,512,952, NMx 4,748,185, Emx 3.
11. **Vectors.** The NMI target `$00:8587` executes 2,629 times: once per frame from 250 to 1207, in no frame of 1208–1328 (121 frames after the Race selection at 1200: a loading phase with NMIs off), then exactly once per frame from 1329 to 2999. No other interrupt vector executes. Steps: branch 10,712,529, JSL 710,137 / RTL 707,466, JMP 329,349, JSR 287,318 / RTS 287,316, JML 6,217, interrupt entry 2,629 / RTI 2,629, unknown 91,477 in 10 distinct edges, all from the same two work RAM sites (`$00:0199` now 88,769 executions under data banks $00, $26 and $80; `$00:019C` 2,708). The MVN/MVP routine in RAM is used heavily during loading.
12. **What the race executes that the boot does not** (the hand-over to M1-02 and M1-03; `compared_to` in the map, "Compared to `boot-start-600`" in the summary): 30,252 byte addresses in 633 ranges are executed only in the race scenario, 4,648 in both, none only in the boot scenario; 1,809 entry points are new, of which 781 are reached by a call, jump, return or interrupt (JSR 137, JSL 61, JMP 121, JML 1, RTS 286, RTL 176, RTI 2, unknown 4) and 1,028 only by branches. By the first frame at which any byte of a new range executes: 40 ranges in frames 500–749 (main menu), 45 in 750–999 (rider and tour screens), 96 in 1000–1249 (track screen and Race), 374 in 1250–1499 (race load and start), 69 in 1500–2249 (riding) and 9 in 2250–2999; none before frame 500. 443 new ranges (19,342 bytes) first execute from frame 1329 (the race running) and 78 (2,055 bytes) from frame 1500 (the riding input) on. Bank $81 (10,225 bytes) is entirely new to the race scenario; the boot scenario never executes it.

### Tooling checks (ROM-free)

13. `tests/tooling/test_coverage.py` (30 tests) covers: the length of all 256 opcodes under all eight modes with the immediate widths checked against hand-derived expectations (8 accumulator immediates follow M, 4 index immediates follow X, REP/SEP/WDM/BRK/COP are fixed 2), the column regularity of the ALU rows, the per-frame drain against a stub ring with the core's semantics (newest entries kept, oldest first on read; steps across frame boundaries; distinct modes and data banks as distinct sites; the overflow and short-ring failures), the coverage document validation, the worker's argument checks, the PNG encoder, the LoROM mapping and mirrors, and on a synthetic 64 KiB ROM image with a synthetic two-frame trace: byte classes summing to the ROM size, lengths following the observed M flag, edge kinds (JSR, JSL, RTS, RTL, branch, RTI, interrupt entry winning over a control-flow predecessor when the target is a vector target), vectors, static references, ranges, unknown edges from a work RAM site, the deterministic dump and the baseline comparison; the CLI's exit codes 2 and 3; and that every tracked map under `docs/map/` is internally consistent, round-trips through the dumper and carries no opcode or mnemonic keys. `test --suite synthetic` grows from 118 to 148 checks.

## Interpretation

The map is what the task asked for: a record of executed bytes with mode context, entry points and vectors, in which every classification traces to an executed instruction or a header vector. Three independent whole-run checks support the decoder: the byte classes partition the ROM with no opcode/operand overlap, every non-sequential step from a ROM site is explained by a control-flow opcode or an interrupt vector target, and the sequence of decoded lengths reproduces the addresses in the samples' trace windows. The unknown edges are exactly the steps from code in work RAM, which the map cannot decode without reading RAM (a data-access capture, out of scope).

The per-frame NMI series makes "once per frame after NMIs are enabled" a measured statement: in the boot scenario it holds from frame 250; in the race scenario the game disables NMIs for frames 1208–1328 while loading the race. The 1.66 % of the ROM executed in the race scenario, all inside the first 128 KiB, is consistent with a small engine plus bank-switched data, but the map does not say what the other 1.875 MiB is; bytes outside the 34,900 executed addresses stay unclassified until a data-access map or a decode (M1-03) classifies them.

What would falsify the laboratory claims: a fresh capture of either manifest whose coverage file digest differs, a sample digest under capture that differs from the manifest's, an unknown edge from a ROM site, or a spot check in which the decoded length of a window instruction does not lead to the next window address. What the interpretation does not cover: the mode of a byte in a *different* scenario (a byte executed under NmX here may execute under NMX elsewhere; multi-mode addresses are listed per scenario), and the meaning of any referenced work RAM address.

## Implementation consequence

- The 65816 opcode length table is `tools/unirally_lab/coverage/opcodes.py` (written for this project from the WDC instruction set description; no emulator table copied). Lengths depend on the pre-instruction M and X flags only; E affects nothing but is recorded.
- Coverage document schema 1 (`coverage.json`, ignored): identity without host paths (ROM digest and size, core library digest, options and method, script digest and frames, scenario id, manifest digest, core commit and patch digest), ring capacity, frames, per-frame instruction deltas, first/last/tail sites, sites `[pc, mode, data_bank, count, first_frame]`, pairs `[pc, mode, data_bank, next_pc, next_mode, next_data_bank, count]`, watched addresses with per-frame counts. Byte-identical for identical runs.
- Map schema 1 (`docs/map/<scenario>.map.json`, tracked, one record per line): identity, mapping rule, totals, vectors with per-frame summaries, banks, ranges (start, end, bytes, ROM offset, opcode/operand bytes, instructions, executions, modes, first frame), multi-mode addresses, entry points (address, kinds with counts, modes, count, distinct sources, first frame, vector name), sites outside ROM, unknown edges, static references (address, region, kinds, references, referencing instructions, executed) and, with `--baseline`, `compared_to`. No ROM bytes, opcode bytes or mnemonics; per-address detail with opcodes goes to the ignored `--detail` artifact.
- Worker additions are additive (`--coverage-out`, `--coverage-ring`, `--coverage-watch`, `--frame-image`, `--frame-image-dir`); without them every output, exit code and digest is unchanged (the M0 suite and the two manifests' digests were re-run on the candidate).
- M1-02 should start from the ranges and entry points that first execute from frame 1329 and 1500 (finding 12) and from the static references into work RAM (968 addresses) and the divergence byte `$7E0313`; M1-03 from the static references into ROM (395) and the fact that no bank above $83 executes.
