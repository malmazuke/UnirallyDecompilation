## Outcome and boundaries

Deliver a validated first schema of the player state in the race scenario and the timing at which it updates, with the tool that shows which instruction reads or writes which address and what it stores.

**Part A — trace-derived access record (D-0002).** The pinned core and patch stay unchanged. During M1-01's per-frame drain of the unchanged trace ring, decode each executed instruction's opcode and operand bytes from the ROM (for pcs in ROM) and, from the registers the same entry carries (A, X, Y, S, D, DBR, P, E), compute:

1. The effective 24-bit address of every direct-page, absolute, long, indexed, stack-relative, push/pull and block-move access, classified as read, write, read-modify-write, stack or block move, with the width (8/16 bit from M/X, or 16/24 for pushes of PEA/PEI/PER/PHD/PHB/PHK) and, for stores and pushes, the exact value stored (from the register in the entry). For block moves (MVN/MVP), per re-execution the source `X` and destination `DBR:Y`; the source bank comes from the operand bytes, which for the work RAM routine at `$00:0199` are read from the end-of-frame work RAM and labelled as such. Loads may take their loaded value from the next entry's register (optional).
2. The residual, counted per (pc, addressing mode) and never guessed: indirect modes (`(dp)`, `[dp]`, `(dp,X)`, `(dp),Y`, `[dp],Y`, `(abs)`, `(abs,X)`, `(sr),Y`) unless resolved from the end-of-frame work RAM when the record shows the pointer bytes were not written in that frame (then labelled `end_of_frame_resolution`); accesses by code executing from work RAM; DMA engine transfers (record the DMA parameter stores to `$43x0`–`$43x6`, `$420B` and `$420C` with their values instead).
3. Aggregation per (pc, mode, effective address, kind): count, first frame, last frame; per address the set of writer and reader pcs; a compact per-frame value log for a list of watched addresses and a register log at watched pcs (frame, A, X, Y, S, D, DBR, P, E per execution). An optional raw work RAM series (a declared range every N frames, written as a binary file plus an index) for differencing between runs.
4. Commands (intended interface; the worker may adjust names and records the final ones here and in `docs/BUILD_AND_VALIDATION.md`): `python3 tools/project.py access capture --manifest <replay manifest> --out <dir> [--from-frame N] [--to-frame N] [--watch-address A ...] [--watch-pc P ...] [--wram-series-range START LENGTH] [--wram-series-every N] --report <json>` and `python3 tools/project.py access query --access <dir>/access.json (--address A | --pc P) [--kind write|read|...]` listing the matching records. Exit codes 0/1/2/3/4 as in the repository convention; reports use schema 1 with `--task M1-02`. The capture checks, like `coverage capture`, that the run's sample digest and final state equal the manifest's.
5. ROM-free tests: the addressing-mode and access-kind classification of all 256 opcodes with the effective address checked against hand-derived expectations for every mode (including the direct-page page wrap in emulation mode when `DL` is zero, the 16-bit `D` offset with its bank-0 wrap, the bank crossing of absolute indexed and absolute-long indexed against the bank-0 wrap of direct-page indexed, stack pushes decrementing `S`, MVN/MVP direction), store widths under M/X, the residual counting, the streaming derivation over a stub ring on a synthetic ROM image (as `test_coverage.py` does), the work RAM series writer and the CLI exit codes 2 and 3.
6. Open notes carried from M1-01 review 1 (last in part A; leave for the handoff if the budget is short): record the core `library_sha256` outside the coverage-digest input so that a regenerated map on another build is byte-identical (regenerate both tracked maps and show they differ only in the expected lines); add the two synthetic cases (an unknown edge from a ROM site; the per-frame vector summary); make `nmi_vector_once_per_frame` require the whole tail from `once_per_frame_from`, not just some frame.

**Part B — the player state and its timing.** Every claim below is tied to a controlled-input experiment whose prediction is written into this record *before* the run (attempts table), and to the writer instruction(s) found in the access record.

1. Candidate discovery by differencing. From the validated race scenario, variants that keep frames 0–1499 identical and change only the riding input: the existing `-right-removed`; Right released at frame 2000 (the reviewer's withheld case in M1-01); Left instead of Right; Down instead of Up; and each of B, Y, A, X, L, R held from frame 1500 together with Right (trick or jump candidates; the M1-01 exploration found B, Y, A, X and Up change work RAM from the first held frame). Each variant is a replay manifest validated by two identical fresh runs (`replay compare` exit 0, digests written into the manifest) and compared against the baseline with `--against`. Work RAM series over the ranges that the race map's 968 static work RAM references cluster in (pages `$00:02`–`$00:16` and `$7E:20`, plus whatever the divergences point to) give the per-frame time series of every differing byte.
2. Interpretations to validate, each with a pre-registered prediction and exact integer arithmetic over at least 500 riding frames: **position along the track** (monotonic while riding right; its per-frame increment equals the speed field in the fixed-point split found; reversed or slowed by Left), **speed** (grows while Right is held, decays after release at 2000, with the increment/decrement constants read from the writer's arithmetic), **race timer** (increments on a fixed frame cadence that matches the on-screen tenths in `--frame-image` dumps; this is the PAL-cadence evidence, do not assume 50 or 60 updates per second), **lean or tilt** (Up changes it and it returns after release), and **one trick or jump state** if a button produces one (a candidate that produces no visible or work RAM effect beyond the joypad image is recorded as unknown, which is acceptable). The **joypad image** bytes (`$7E0313` and neighbours) are identified as such, with the instruction that reads `$4218`/`$4219` and stores them. Since the race is MIKE vs BRONSEN, check whether the opponent's state has the same layout at a fixed stride (the opponent moves in the `-right-removed` run while the player does not); a second instance with the same writers is strong support for the layout.
3. Writers and timing. For each validated field: the writer pc(s) with mode and kind, the per-frame execution count of the primary writer over the riding phase (from the per-frame register log or the coverage watch), and the order within one frame of the joypad read, the field updates and the sample point (end of `retro_run`, R-0003). State whether one game update is one PAL frame in this scenario, how the 1208–1328 NMI-off loading phase and the first riding frames behave, and define the **capture phase** for M2: which frame's inputs the sample at the end of frame N reflects (M0-04 showed `$7E0073` following Start and M1-01 `$7E0313` following Right in the same frame).
4. Deliverables: `docs/state/player-state.md` (schema v1: per field the address, width, signedness, units or fixed-point split, instances, writer pcs, the validating experiment, confidence and open questions; a section of what is unknown); `tests/manifests/fields/player-state-v1.json` declaring the validated fields as named work RAM ranges in the replay manifest `fields` format; a replay manifest with the race scenario's inputs and those fields declared (`race-crawler-dragster-3000-fields.json` or similar), validated by two identical fresh runs, whose `--against` comparison with the Right-removed variant names the field that diverges first; the evidence record R-0007; the ROM-free tests; this record's handoff.

Not in scope: decoding any track, tile or sprite (M1-03), the meaning of opponent AI beyond identifying its state instance, other tracks, tours, riders or modes, a native simulation or any constant tuning, a core patch change (D-0002 fallback is a separate task), changes to the frozen manifests, the samples/coverage/map schemas or `docs/STATE.md`.

Tracked-content rule: tracked files carry addresses, widths, counts, frames, register values at stores to hardware registers and field descriptions; no ROM bytes, opcode bytes, disassembly listings or work RAM dumps (those stay in ignored `artifacts/`). Values of work RAM bytes may be quoted in R-0007 and `docs/state/` where they support a claim (a timer series, a position series).
